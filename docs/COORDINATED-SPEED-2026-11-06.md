# 速度装備の共同配分で局所的な行き止まりを回避

## 問題

1枠ずつの装備変更と2人の交換では、速度不足がいったん増える変更を採用できなかった。先頭の補助役を速くし、2番目と主力へ別々の速度装備を渡せば成立する場合でも、途中の単独変更が不利なため調整が止まる。

## 変更

通常の速度調整が止まり、速度条件が未達かつ評価枠・時間が残っている場合だけ、防具の同じ部位を最大4人で一括して配分する候補を追加する。武器・職業・左手・継承・行動列は変更しない。こころの共同配分や複数部位の同時変更は対象外。

- 各部位について、現在の装備・所持する速度上位4候補・空欄を検討する。1つの装備を複製しない。
- 他の部位で使用中の個数を引いてから配分し、全体の所持数と職業条件・HP・速度・こころコストを検査する。
- 途中の配分が不利でも破棄せず、4人分が完成してから比較する。速度の上下限から成立しない枝を除く。
- 残す上位候補は最大8件。調整1回の全体で共同配分の探索ノードは2,048件までとし、締切も確認する。能力の組立て検査と戦闘全体の評価回数は別に数える。
- 最終候補は既存の全行動計算で検査し、MP・習得技・バフ・シールド・生存等を省略しない。元の手順が討伐できた場合は討伐条件も維持する。
- 戦闘全体の評価は従来の速度調整予算に含める。候補数や総時間の上限を増やさない。

`atomicSpeedRepair:false` で新しい共同配分だけを無効化できる。従来の1枠変更と2人の交換は残る。`SpeedTuner26.tune` の `coordinatedChecks` は共同配分の探索ノード、`coordinatedCalls` は実際に戦闘全体を再評価した件数。統合探索の `orderRepair.coordinatedCalls` は順序必須の前後段調整で使った分を合計する。

## 比較ケース

仮基礎能力と架空の速度帽を使った構造ケースで、通常調整は表示速度100/380/200/100で停止し、味方順が未達だった。共同配分は3人を同時に変更し、200/880/350/100で指定した速度比1.2・敵速度50を満たした。

同じ128回上限で、通常調整8回の未達に対し、共同配分ありは9回で成立した。共同配分の探索ノードは24件、追加の戦闘評価は1回。与ダメージ41,722は維持し、厳密条件での再計算も一致した。時間の高速化や実機の速度保証を示す結果ではない。

統合探索の既存構造ケースでは、無効・有効とも782件の評価で最良火力142,928と順序成立を維持した。このケースは共同配分を必要とせず、全体火力向上の証明にはならない。

所持する帽子3個と空欄の小規模な全組み合わせを照合し、唯一の順序成立配分へ到達した。未所持品、資源条件を満たさない評価、件数上限と期限切れ、元プロフィール・手順の不変も検査する。

```
npm run benchmark:speed
node scripts/benchmark-search.cjs --late-order-only --without-atomic-speed-repair
node scripts/benchmark-search.cjs --late-order-only
```

## 制限

候補を絞る近似探索であり、全装備の最適性や所持品全体での成立可否を証明しない。部位をまたぐ変更、こころ・防具の同時変更、候補外の装備で初めて成立する組合せは取りこぼしうる。速度範囲による枝刈りは元手順の状態倍率を使い、最終的には再計算した実際の状態で検証する。火力やブレイク枚数の最適性も保証しない。
